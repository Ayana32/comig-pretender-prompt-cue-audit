# LLM Judge Prompt v1

## Purpose

This prompt asks an LLM judge to identify which of two anonymised responses was written by the human anchor author. It audits LLM-judge behaviour; it is not a substitute for a COMIG human judge and does not produce human identification accuracy.

## Prompt template

```text
You are evaluating two anonymised answers to the same question. One answer was written by a human postgraduate researcher in speech and natural language processing, and the other was generated by an AI system.

Question:
{question}

Response A:
{response_a}

Response B:
{response_b}

Decide which response was written by the human.

Choose exactly one response, A or B. Do not choose a tie. Report confidence as an integer from 50 to 100, where 50 means a forced choice with no meaningful confidence and 100 means completely certain. Give a concise justification of 2 to 4 sentences, approximately 40 to 100 words, referring to evidence in the responses. Do not reveal hidden chain-of-thought; provide only a brief decision rationale.

Return exactly one JSON object with no Markdown fence and no text before or after it, using this schema:
{
  "selected_human_response": "A" | "B",
  "confidence": <integer from 50 to 100>,
  "justification": "<2 to 4 sentence rationale>"
}
```

## Output contract

| Field | Type | Allowed values | Meaning |
|---|---|---|---|
| `selected_human_response` | string | `A`, `B` | Forced authorship selection |
| `confidence` | integer | `50` to `100` inclusive | Confidence in the forced selection |
| `justification` | string | 2 to 4 sentences; target 40 to 100 words | Concise evidence for the selection |

The response is parse-valid only if it is a single JSON object, contains exactly the three required fields, and all values satisfy the allowed types and ranges. Raw output is retained whether valid or invalid.

## Tie and invalid-output policy

Ties are not allowed because the audit mirrors COMIG's forced identification task. A judge output that returns a tie, both/neither, a null selection, an out-of-range confidence value, missing fields, or unparseable JSON is marked `INVALID`; it is never silently converted to A or B. The raw output and failure reason are retained. During Q0, recurrent failures may motivate a documented v1.1 formatting revision or judge-model replacement. After main generation begins, the prompt is not revised.

## Presentation and repetition rules

- Q1–Q8 use the pre-specified original A/B schedule in `protocol.md`; the swapped evaluation reverses that exact placement.
- Question and response text are identical across original and swapped evaluations; only A/B placement changes.
- The same v1 prompt and schema are used for both judge models and both prompt conditions.
- Each judge call is independent; previous selections and justifications are not supplied.
- The judge is not given the codebook, the prompt-condition label, the true authorship label, or outputs from the other judge.

## Version rule

Version v1 is frozen before Q0 judge calls. If Q0 reveals systematic parsing failure, a v1.1 revision may change formatting instructions or schema presentation only. The change, reason, and affected calls must be recorded, and Q0 must be rerun. Substantive decision instructions must not be changed without declaring a new protocol version.
